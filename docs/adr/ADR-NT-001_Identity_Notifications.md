# ADR-NT-001 — Identity-owned Notifications, consent and delivery isolation

**Structural decision APPROVED: GD-03/GD-06, owner, 27 November 2026 11:31 UTC; requirements FP-NT approved 12:26 UTC.** Implementation, provider credentials and final security review remain open (#309, #140, #141). No separate Notifications service.

Identity owns notification inbox, preferences, device registrations, purpose-based consent, versioned templates and delivery attempts. Extend existing `NotificationPreferences` and mail sender; do not create a second preferences authority. Dispatcher process `notify-dispatch` uses `identity_notify_rt` with notification/consent tables and a restricted account-contact view (id, current email, locale, active status); it cannot read password, session, MFA or step-up tables. Migration owner is separate; broker account `identity_notify` can consume only `kolovibe.identity.notify` and publish only allowed outcome/Audit destinations. It cannot consume the Identity privacy queue. FCM/APNs/SMTP secrets are scoped to the dispatcher and provider calls exist only there.

Domain services commit facts plus outbox. Recipient resolver authenticates producer/type, checks current visibility, account activity, block lists and preferences through owner APIs, then creates unique `(producer,event_id,recipient,key)` inbox+channel records atomically. No service sends free-form recipient addresses. Claim delivery with a bounded lease, retry transient provider failures with backoff, revoke invalid tokens, keep inbox working during push outage. Provider delivery is **at least once**: after provider acceptance but before database commit a retry can duplicate a push unless the provider supports dedupe. Stable delivery ids/collapse keys and client dedupe mitigate this; do not claim exactly-once external delivery.

Device registration binds token to the active session/account; transfer of an existing token invalidates its earlier association. Revoke on logout, session revoke, erasure or invalid-token result. A privileged inbox read is never available. Console sees counts, template status and channel metrics only, with administrator+MFA and audited configuration mutations. Deep links contain opaque target ids and reauthorize on open; push contains generic text, no names, messages, financial amounts, credentials or one-time links. Quiet hours and rate limits are policy-driven; security/transactional exceptions follow FP-NT. Marketing is disabled for the first release.

Consent is account data in Identity, separate from legal acceptance and notification preferences. Unique purpose/version/evidence records are append-only history with revocation, timestamp and wording digest; current state is derived. Advertising reads a minimal signed assertion for the specific purpose; a missing/expired/revoked assertion denies delivery. UMP and OS permission results never override server restrictions on age/consent. Exact legal purposes and retention remain owner/legal decisions.

Erasure/export include notification data; deletion-completion delivery requires the approved lifecycle policy and cannot depend on an inbox deleted by the same request. Delivery/dead-letter retention, retry ceilings and provider ownership remain tracked in #136/#311/#309. No credentials or provider are selected by this ADR.

API and RabbitMQ details have one authority: [DOC-205](../architecture/DOC-205_OpenAPI_3_1_DRAFT.yaml), [event catalogue](../../packages/contracts/events/catalogue.yaml). Requirement authority: [FP-NT](../requirements/FP-NT_Notifications_Requirements_PROPOSED.md). Rejected alternatives: a thirteenth service (unnecessary contact duplication) or provider calls in each domain (duplicated policy/delivery).
